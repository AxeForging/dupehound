# 002 — Scale and recall: bounded memory, detection beyond function bodies

**Status:** draft, awaiting review. Of the *Design* section, only the rolling hash
(memory step 3), the streaming dead-code usage pass (step 6) and an
estimate-based `--max-memory` and the recall change are implemented; disk spill,
compact tokens and parallel lexing are not.
The *Already fixed* section describes what shipped on the same branch as this spec.

## Context

dupehound was evaluated against SonarQube Community Build 26.10 on seven public
repositories of 170k–800k lines each, one per major language family. Both tools
scanned the same files; every dupehound run was confined to a 3 GB memory cgroup.

Sonar is a second opinion, not ground truth: it matches near-verbatim text at
100 tokens / 10 lines, while dupehound also normalizes identifiers and defaults to
50 tokens, so dupehound legitimately reports more. The comparison that matters is
recall — duplication Sonar sees and dupehound does not — measured with dupehound
set to Sonar's 100-token threshold.

code that Sonar does not report) found them to be real, refactorable duplication
— renamed copies of the same logic. That is dupehound's advantage and it holds.

## Already fixed on this branch

Each was reproduced with a failing test first.

1. **Memory blow-up.** Clone previews were substrings of the file just read, so
   every clone instance pinned a private copy of its whole file. Terraform peak
   went from 7.5 GB to 1.1 GB in exact-only mode with identical findings.
2. **Wrong line numbers.** A quote left open on its line (Rust lifetimes, JSX
   apostrophes, each line of an unsupported multi-line string) counted the
   newline twice, shifting every later clone in the file. tokio had 19 clone
   instances reported past the end of their file; now 0. Triple-quoted strings
   are lexed in seven more languages and Rust lifetimes are no longer strings.
3. **Dead-code noise.** Functions invoked by a runtime or test runner were
   reported as dead: 3,938 → 48 findings on terraform, 14,967 → 139 on django,
   1,874 → 77 on tokio.
4. **Hand-written files skipped as generated.** Prose like "the hash code is
   generated by…" in a doc comment removed the file from the scan. 20 of the 22
   files skipped in guava were hand-written and held 7,035 duplicated lines.
5. **Shell functions.** Only `function name` was recognised, not `name() { … }`.

### Recall change, implemented on the same branch

`--scope file` (now the default) detects type-1/2 clones across the whole file.
Measured with dupehound at Sonar's 100-token threshold; "reported" is duplicate
lines at default settings.

| repo | Sonar lines found: function → file | Sonar files found | reported lines | wall / peak (file scope) |
|---|---:|---:|---:|---:|
| tokio | 38% → 96% | 63% → 94% | +101% | 2.5s / 334 MB |
| nest | 86% → 94% | 78% → 93% | +14% | 6.7s / 641 MB |
| django | 77% → 92% | 70% → 94% | +27% | 11.1s / 1.7 GB |
| rails | 27% → 76% | 32% → 76% | +60% | 11.6s / 1.6 GB |
| laravel | 57% → 89% | 75% → 96% | +44% | 15.7s / 1.6 GB |
| guava | 98% → 98% | 91% → 92% | +1% | 5.9s / 0.9 GB |
| terraform | 85% → 88% | 90% → 93% | +8% | 20.8s / 1.9 GB |

How it works, and why each rule exists:

- Windows may leave a function body and span several, so a class copied
  wholesale is one clone even when every method is a few lines long.
- Outside function bodies identifiers must match by name. Declarations are all
  the same shape; matching them loosely reported every class against every other.
  For Java, C, C++, C# and Dart "function body" is narrowed to blocks that follow
  a parameter list, because the existing heuristic also covers class bodies.
- Literal values may still differ outside function bodies (two statements that
  differ only in the strings they pass are the same statement) — except inside
  a data literal, where they must match, so two translation or fixture tables
  of the same shape are not clones.
- Import, include, use and package statements are skipped.
- Type-3 detection is unchanged and stays inside function bodies.
- Ruby, shell and PHP heredocs are lexed as one string literal.

Against the requirements below: R4 (85% of Sonar's lines) is met on six of
seven repositories; rails reaches 76%. What rails still misses is repetition
whose bulk is heredoc text, which Sonar counts line by line and dupehound holds
as a single token. R5 (reported duplication grows by at most 25%) is not met
and was the wrong measure: growth is largest exactly where function-only
detection found least. Twenty findings that only file scope reports were
sampled at random across tokio, rails, laravel and django; all twenty were
real duplicated code. That is a sample, not a precision figure.

kubernetes in file scope, exact mode: 13.0 s, 3.7 GB peak, 40,883 clones.

## Problems this spec addresses

### P1 — Memory is unbounded

There is no memory budget. `--max-files`, `--max-pairs` and `--max-file-size` cap
counts and CPU time; nothing caps bytes. After fix 1, memory is still linear in
repository size with a large constant, because the whole pipeline is in RAM:

| structure | cost | where |
|---|---|---|
| `Token` | 56 bytes each, plus the source text it slices into | `tokenizer.go` |
| window hashes | 8 bytes per token, recomputed over `min-tokens` tokens per position | `detectExact` |
| hash index | a map entry and slice for every window, including unique ones | `detectExact` |
| fuzzy blocks | ~34 hashes per token position at default settings, plus an inverted index (estimated ≈ 600 bytes per position from the code, not measured) | `detectFuzzy` |
| dead-code usage map | a map entry per identifier occurrence in the repository | `findDeadFunctions` |

Tokenization and detection are also single-threaded (≈ 100% of one core on a
16-core machine).

### P2 — Detection is confined to single function bodies

A window must sit entirely inside one function body. Two consequences, both
measured:

- **Code outside a recognised function is invisible.** Rails tests are written as
  `test "…" do` blocks, not `def`: dupehound finds 29% of the lines Sonar reports
  there. The same applies to top-level scripts, class bodies and macros.
- **A clone cannot span functions.** Laravel's `AbstractPaginator.php` and
  `AbstractCursorPaginator.php` share about 1,000 identical lines; Sonar reports
  ~530 duplicated lines, dupehound reports 38 at default settings and none at 100
  tokens, because the classes are made of 4–6 line methods.

An experiment that simply treated every token as in scope, at 100 tokens:

| repo | Sonar files found | Sonar lines found |
|---|---:|---:|
| rails | 30% → 78% | 27% → 78% |
| laravel | 75% → 96% | 57% → 89% |
| nest | 78% → 93% | 86% → 94% |
| django | 68% → 95% | 75% → 89% |

It also raised reported duplication by 1.3× (nest) to 2.4× (rails), so it cannot
ship as-is: imports, declarations and data tables would flood the output.

## Requirements

- R1. A scan never exceeds a configurable memory budget (`--max-memory`,
  default derived from available memory). When the budget forces reduced
  coverage, the report says so through the existing `partial` fields.
- R2. Results are identical with and without spilling, and deterministic.
- R3. kubernetes completes in exact-only mode under 2 GB.
- R4. Recall against Sonar at 100 tokens reaches at least 85% of lines on every
  repository in the table above.
- R5. Reported duplication on those repositories grows by no more than 25%
  relative to this branch at default settings, so the recall gain is not paid for
  with noise. (The naive experiment fails this.)
- R6. Wall time does not regress on any repository in the table.

## Design

### Memory (P1)

1. **Compact tokens.** Store kind (1 byte), line (4 bytes) and an interned text
   id (4 bytes) in parallel slices; release the source text after lexing. Roughly
   12 bytes per token instead of 56 plus source.
2. **Parallel lexing.** A worker pool sized to the CPU count tokenizes files;
   results are merged in path order to keep output deterministic.
3. **Rolling hash.** Replace the per-position FNV over `min-tokens` tokens with a
   polynomial rolling hash: O(1) per position instead of O(`min-tokens`).
4. **Sort-based grouping with spill.** Instead of a map holding every window,
   emit `(hash, file, position)` records, partition them by hash prefix into
   shards, and group one shard at a time. Shards that do not fit the budget are
   written to a temp directory and read back one by one. This is the piece that
   makes memory bounded rather than merely smaller.
5. **Fuzzy detection on sketches.** Replace the per-position mini-hash sets with
   a fixed-size sketch per candidate region, built only over regions exact
   detection left uncovered.
6. **Dead-code usage as counts.** Keep, per identifier, a count and the first
   two locations — enough to answer "is it used anywhere else?".

Steps 1–3 and 6 are independent and safe to land first. Step 4 is the
architectural change. Step 5 changes type-3 results and needs its own evaluation.

### Recall (P2)

Invert the mask: detect over all tokens, and exclude what is known to be
declarative rather than include what is known to be a function body.

- Excluded: import/include/use/package lines, and the existing single-literal
  rule for data tables.
- Function spans are kept, but only for attribution (`function` in the report)
  and for the dead-code pass.
- Windows may cross function boundaries, so a file copied wholesale is reported
  as one large clone rather than missed.

The exclusion list is the risk. It is tuned against R4 and R5 together, per
language, using the evaluation below.

## Evaluation and test plan

- Unit tests per change, written first, as for the fixes above.
- A memory regression test per structure changed (the pattern in
  `services/preview_test.go`).
- Before/after runs of the seven-repository comparison, reporting recall, total
  reported duplication, wall time and peak RSS under a cgroup cap. A change lands
  only if R4–R6 hold on all seven.
- kubernetes as the scale gate for R3.

## Rollout

Two pull requests, memory first: it is behaviour-preserving and verifiable by
identical output. The recall change alters findings, so it ships behind a flag
for one release, with the old behaviour as default, then flips.

## Smaller findings, not covered above

- `.dupehound.yml` is discovered from the working directory, not from `--path`,
  so scanning another repository applies the caller's excludes to it.
- Directories named `build`, `dist`, `target` and `testdata` are always skipped,
  with no way to opt back in; `.gitignore` is not consulted.
- Type-3 clones are always exactly `min-tokens` long and always pairs; adjacent
  matches are not merged into one region.
- Dead-code detection for JS/TS does not see class methods, and for C, C++,
  Java, C# and Dart treats any `name(` outside a body as a definition.
- There are no benchmarks and no test that exercises a large input.
- Window hashes are compared without verifying the tokens, and hash value 0 is
  used as "no window".
